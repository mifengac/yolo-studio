## 一、P0-A ★ 启动时可能误杀无关进程（第一轮新引入，最高优先级）

- **位置**：`app/services/train_svc.py:590`（`recover_interrupted_jobs`）、`:620`（`_kill_pid`）、`:580`（`_pid_alive`）
- **背景**：第一轮把"pid 存活判断不可靠"改成了更彻底的方案——启动时把所有 `running` 任务无条件标 `interrupted`，若 pid 还活着就杀掉。**这个方向是对的**，队列不会再被幽灵任务卡死，本轮保留该思路。
- **新引入的问题**：`data/app.db` 里存的 pid 来自**上一次运行**。容器重启后 pid 从小数字重新分配，旧 pid 极易被无关进程占用。此时：
  ```python
  if _pid_alive(r["pid"]):
      _kill_pid(int(r["pid"]))     # ← 杀掉的可能是完全无关的进程
  ```
  而 `_kill_pid` 内部第一步是 `os.killpg(pid, SIGTERM)`，**杀的是整个进程组**。训练进程是用 `start_new_session=True` 启动的（`train_svc.py:409`），自己就是组长，`pid == pgid`；一旦这个 pid 被复用给容器里另一个组长进程（比如 uvicorn 主进程），`killpg` 会把那个进程组整个端掉——最坏情况是应用把自己杀了。
- **改法**：杀之前必须确认"这个 pid 确实是我们那个训练进程"。新增一个校验函数：
  ```python
  def _is_our_train_process(pid: int, job: dict) -> bool:
      """读 /proc/<pid>/cmdline 确认是本 job 的训练进程。"""
      try:
          raw = Path(f"/proc/{pid}/cmdline").read_bytes()
      except (OSError, PermissionError):
          return False
      cmdline = raw.replace(b"\0", b" ").decode("utf-8", "ignore")
      run_dir = str(job.get("run_dir") or "")
      return "ultralytics" in cmdline and bool(run_dir) and run_dir in cmdline
  ```
  在 `recover_interrupted_jobs` 里改成：
  ```python
  pid = r["pid"]
  if pid and _pid_alive(pid) and _is_our_train_process(int(pid), dict(r)):
      _kill_pid(int(pid))
  elif pid and _pid_alive(pid):
      logger.warning("pid=%s 存活但不是本 job 的训练进程（疑似 pid 复用），跳过终止", pid)
  # 无论哪种情况，都照常标 interrupted
  ```
- **注意**：`kill_running_train_processes()`（`:642`，关服务时调用）的 pid 是**当前进程刚启动的**，可信，那条路径可以不加校验；但加上也无害，建议统一走同一个校验函数，避免以后有人复制粘贴。
- **另外**：确认训练启动时写入 `train_job.run_dir` 的是**绝对路径**，否则上面的 `run_dir in cmdline` 匹配不上。若存的是相对路径，校验里两边都做 `os.path.abspath` 归一化。
- **验收**：
  1. 正常场景：训练跑一半 `docker compose restart`，任务标为 `interrupted` 且可「继续训练」
  2. 误杀防护：手工把 `data/app.db` 里某条 `running` 任务的 pid 改成一个无关的存活进程 pid（比如 `sleep 9999` 的 pid），重启服务后，**那个进程必须还活着**，日志里出现"疑似 pid 复用，跳过终止"，同时该任务被标为 `interrupted`

## 二、P0-B ★ torch 版本对不上，内网交付会翻车

- **位置**：`requirements.txt:1-3`、`Dockerfile:32`、`Dockerfile:76`、`run.sh`
- **现状**：

  | | 版本 |
  |---|---|
  | 本地 venv 实际运行并通过冒烟的 | torch **2.13.0+cpu** / ultralytics **8.4.105** |
  | requirements.txt 与 Dockerfile 钉的 | torch **2.5.1** / torchvision **0.20.1** |

  `2.5.1` 是 2024 年 10 月的版本。等于**本地验证过的环境和交付进内网的环境不是同一个**。ultralytics 8.4.105 配两年前的 torch 很可能不兼容，yolo26 属较新架构，对 torch 版本也有要求。这类问题在内网爆发时最难处理——没网、装不了包、只能整个镜像重做。

- **改法**：
  1. 以**本地实测通过的版本为准**统一三处：`requirements.txt`、`Dockerfile:32`、`run.sh`
     ```
     --extra-index-url https://download.pytorch.org/whl/cpu
     torch==2.13.0+cpu
     torchvision==<与 torch 2.13.0 配套的版本>+cpu
     ```
     配套的 torchvision 版本请用 `.venv/bin/pip show torchvision` 查本地实际值，**不要凭印象填**。
  2. 其余依赖也一并钉死（把 `>=` 改成 `==`），版本号取本地 `.venv/bin/pip freeze` 的实际值。离线交付必须可复现。
  3. **`Dockerfile:76` 的断言是假的，必须修**：
     ```python
     assert "+cpu" in torch.__version__ or not torch.cuda.is_available()
     ```
     CPU-only 镜像里 `torch.cuda.is_available()` 恒为 `False`，`not False` 恒为 `True`，**整个断言永远通过**——装成 2.5GB 的 CUDA 版也检测不出来。改成：
     ```python
     assert "+cpu" in torch.__version__, f"必须是 CPU 版 torch，实际: {torch.__version__}"
     ```
- **验收**（这条必须真跑，不能只改文件）：
  1. 有网机器上 `docker build` 成功
  2. `docker run --rm yolo-studio:latest python -c "import torch,ultralytics;print(torch.__version__, ultralytics.__version__)"` → torch 带 `+cpu`，版本与本地一致
  3. 镜像体积 < 2 GB（`docker images` 确认）
  4. **容器里跑通冒烟**：`docker compose up -d` 后 `python scripts/smoke_test.py --train`，训练能真正跑完 2 epoch 出 `best.pt`
  5. 故意把 Dockerfile 的 torch 改成 CUDA 版试一次，断言必须**报错**（验证保险是真的）——验证完记得改回来

## 三、P0-C ★ 任务线程池轻重不分（第一轮遗留，且已被放大）

- **位置**：`app/tasks.py:35`（`max_workers=2`）、`:18`（`_heavy_lock`）、`:149-162`（heavy 判定与加锁）、`:193`（释放）
- **现状**：整个系统只有 **2 个 worker 名额**，重任务又靠一把全局锁串行。第一轮往 heavy 集合里又加了 `import_video` 和 `openvino_export` 两个类型，**问题被放大了**：训练跑着的时候，只要再来一个重任务（例如发布模型触发的 OpenVINO 导出），两个名额就被占光——第 2 个任务只是阻塞在 `_heavy_lock.acquire()` 上干等，却占着 worker 名额不放，导致缩略图生成、导出小文件等轻活**全部堵死**，用户会觉得"训练一开界面就卡死了"。
- **改法**：拆成两个池。
  ```python
  _heavy_executor = ThreadPoolExecutor(max_workers=1, thread_name_prefix="ys-heavy")
  _light_executor = ThreadPoolExecutor(max_workers=4, thread_name_prefix="ys-light")
  ```
  1. 把 heavy 类型集合提成 `app/config.py` 里的常量 `HEAVY_TASK_TYPES`（当前值：`autolabel`、`openvocab`、`track`、`train`、`train_resume`、`export`、`evaluate`、`openvino_export`、`import_video`），避免以后新增类型再漏
  2. 投递时按类型选池：heavy 走 `_heavy_executor`，其余走 `_light_executor`
  3. **重任务池 `max_workers=1` 本身就是串行的，可以直接删掉 `_heavy_lock`**——顺带消除"锁被异常路径永久占住"的隐患。删除时确认 `:162` 的 `acquire` 与 `:193` 的 `release` 成对逻辑一并清理干净，不要留下半截
  4. `stop_workers()` 要同时关闭两个池
  5. 排队中的重任务仍要保留"等待其他重任务结束…"的状态文案——现在靠锁实现，改成池之后要在投递时判断队列非空来设置，不能把这个用户提示弄丢了
- **验收**：
  1. 启动一个训练任务，同时发起预标注 → 预标注显示"等待其他重任务结束…"，**不抢 CPU**
  2. 上述状态下，浏览数据集、翻标注页缩略图**依然流畅**（这是本条的核心目的）
  3. 连续投递 3 个重任务，逐个串行执行，无并发

### P1-F SAM 缓存要缓存 embedding，不是缓存图片（第一轮未达成）

- **位置**：`app/services/sam_svc.py:61`（`_load_rgb`）、`:93`（`model.predict`）、`:140`（`prefetch_next`）
- **现状**：第一轮补上了缓存调用，但**缓存的是 numpy RGB 数组，不是 SAM 的 image embedding**。两者耗时差两个数量级：
  - 图片解码（现在缓存的这个）：几十毫秒
  - **SAM image encoder 前向传播（真正的瓶颈）：CPU 上 1.5~3 秒**

  `model.predict(source=arr, points=...)` 每次调用仍会把 encoder 完整跑一遍。验收标准要求"同一张图第二次点选 < 200ms"，当前实现**必然不达标**，还是 1.5~3 秒。在这台纯 CPU 机器上，SAM 辅助标注的价值基本被抵消了。
- **改法**：改用 ultralytics 的 `SAMPredictor` 接口，把"编码"和"提示推理"拆开：
  ```python
  from ultralytics.models.sam import Predictor as SAMPredictor
  # 每张图只做一次：
  predictor.set_image(arr)          # ← 昂贵的 encoder 在这里
  # 之后同一张图的多次点选复用上面的结果：
  results = predictor(points=pts, labels=labs)
  ```
  1. 缓存的对象改为"已 `set_image` 的 predictor 状态"（或其 `features`），key 仍是 `image_id`
  2. `_MAX`（`config.SAM_EMBED_CACHE_SIZE`）要重新评估——embedding 比 RGB 数组占内存大得多，建议默认降到 **4**，并在配置注释里写明每条约占多少内存
  3. `prefetch_next`（`:140`）改成真正预热 embedding，放后台线程执行，**不要阻塞当前请求**
  4. 具体 API 名称请以本地实际安装的 ultralytics 8.4.105 为准（`.venv/bin/python -c "from ultralytics.models.sam import Predictor; help(Predictor)"`），不要照抄本文档里的示意代码
- **前置条件**：`weights/mobile_sam.pt` 目前**不在本机**，需要先备齐才能验证。如果拿不到权重，本条挂起并在 README「待确认事项」里注明，**不要改了却没验证就说做完了**。
- **验收**：同一张图第一次点选 1.5~3 秒（可接受），**第二次及以后 < 200 ms**；切换到下一张图时，后台预热不会让界面卡顿。

### P1-G 去重改真 pHash + 分桶（第一轮未做）

- **位置**：`app/services/dedup_svc.py:16`（`_average_hash`）、`:87-90`（O(n²) 两两比较）
- **现状**：第一轮只把 docstring 从"pHash"改成了"aHash（非 pHash）"——诚实标注了，但问题还在。aHash 只是缩放到 8×8 取灰度均值，**对亮度变化极其敏感**，而卡口图片白天/夜间/逆光差异巨大，正是 aHash 最不擅长的场景，会大量漏判近重复。
- **改法**：
  1. 实现真 pHash：缩放到 32×32 → DCT → 取左上 8×8 低频区（**排除直流分量 [0,0]**）→ 与中位数比较取二值。用 numpy 实现即可（`scipy` 不必引入，DCT 可用 numpy 手写或用 `cv2.dct`，项目已有 opencv）
  2. 干掉 O(n²)：`:87` 的双层循环在 5000 张时是 1250 万次比较。改用**分桶**——把 64 位哈希切成 4 段 16 位，建 4 个倒排索引，只有至少一段完全相同的候选对才进入精确汉明距离比较
  3. 字段名 `image.phash` 保持不变；**已有数据的 aHash 值与新 pHash 不兼容**，迁移时要把旧值清空（`UPDATE image SET phash=NULL`）让其重算，或加版本前缀区分，不能直接混用
- **验收**：5000 张图去重任务 2 分钟内完成；准备一对同场景的白天/夜间图，**不应**被判为重复；准备一对真正的近重复图（同一段视频相邻帧），**应该**被判为重复。
