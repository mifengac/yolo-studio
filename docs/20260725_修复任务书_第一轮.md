## 一、先理解一个贯穿性根因（很重要，能一次性避免同类 bug）

本项目有多处代码想表达"用户没传这个参数，我来决定默认值"，写法是：

```python
if "epochs" not in params:      # 或 if not model
    epochs = 20
```

但参数来自 Pydantic 模型，而模型里给了默认值：

```python
class TrainRequest(BaseModel):
    epochs: int = 40            # ← 有默认值
```

Pydantic 序列化后 `params` **永远**包含 `epochs`，所以那个分支永远走不到，业务默认值成了死代码。

**统一改法**：凡是"后端需要区分用户到底传没传"的字段，Pydantic 里一律声明为 `Optional[X] = None`，业务层判断 `is None`。本轮的 P0-1 和 P1-2 都是这个根因，请一并按此原则排查同类写法。

## 二、P0 —— 必修（不修系统关键路径不可用）

### P0-1 闭环失效：默认预标注模型永远不生效 ★最严重

- **位置**：`app/schemas.py:38`、`app/api/autolabel.py:22-24`
- **现状**：
  ```python
  class AutolabelRequest(BaseModel):
      model: str = "weights/0517_yolo26s_wheelie_multi-rider.pt"   # 硬编码
  ```
  导致 `autolabel.py` 里的
  ```python
  if not model or model in ("default", "auto"):
      model = model_svc.get_default_autolabel_path() or body.model
  ```
  永远为假，`get_default_autolabel_path()` 是死代码。用户在模型仓库里"设为默认预标注模型"后，预标注仍然调旧模型。
- **后果**：直接挂掉设计文档验收标准中的「闭环」一项——这是整个产品的核心卖点。
- **改法**：
  1. `schemas.py`：`model: Optional[str] = None`
  2. `autolabel.py`：`model = body.model or model_svc.get_default_autolabel_path() or config.FALLBACK_AUTOLABEL_MODEL`
  3. 兜底常量放 `app/config.py`，值为 `weights/0517_yolo26s_wheelie_multi-rider.pt`，并允许 `.env` 覆盖
  4. 检查前端 `web/js/app.js` 调用预标注处，确认不传 `model` 字段时能走到默认模型
- **验收**：注册一个新模型 → 设为默认 → 发起预标注 → 任务详情里的 `model` 参数应是新模型路径，且 `data/logs/app.log` 中加载的是该模型。

### P0-2 标注页键盘/鼠标事件重复绑定

- **位置**：`web/js/labeler.js:106-113`（`bindUi` 内）、调用方 `web/js/app.js:100`
- **现状**：`bindUi()` 向 `window` 注册了 `mousemove`、`mouseup`、`keydown`、`keyup`、`resize` 五个监听，**从不移除**；而 `app.js:100` 每次进入标注页都调一次 `YSLabeler.mount()` → `bindUi()`。
- **后果**：第二次进入标注页后，按一次 `A`/`D` 跳**两张**图，第三次跳三张；所有快捷键行为翻倍，标注体验直接崩坏。
- **改法**（二选一，推荐第 1 种）：
  1. 模块内保存监听器引用，新增 `unmount()` 做 `removeEventListener`，并在 `app.js` 切换页面时调用；`mount()` 开头先 `unmount()` 保证幂等。
  2. 把 window 级监听抽到模块加载时**只绑一次**，处理函数内部用 `if (!mounted) return;` 守卫。
- **验收**：进标注页 → 退回数据集页 → 再进标注页，按一次 `D` 只前进一张图。反复进出 5 次仍正常。

### P0-3 requirements.txt 缺 CPU 版 torch

- **位置**：`requirements.txt`（当前 9 行，无 torch）
- **现状**：Dockerfile 里单独装了 CPU torch 并有 `+cpu` 断言，所以**镜像没问题**；但本地开发 `pip install -r requirements.txt` 时，ultralytics 会从 PyPI 拉 **CUDA 版 torch（约 2.5 GB）**，在无 GPU 机器上纯属浪费，且 `run.sh:9` 装 torch 时没钉版本，离线交付不可复现。
- **改法**：在 `requirements.txt` 顶部加
  ```
  --extra-index-url https://download.pytorch.org/whl/cpu
  torch==2.5.1+cpu
  torchvision==0.20.1+cpu
  ```
  并把 `run.sh` 里裸装 torch 的那行删掉（改由 requirements 统一管理）。同时把其余依赖从 `>=` 改成 `==` 钉死版本，离线交付要可复现。
- **验收**：干净 venv 里 `pip install -r requirements.txt` 后，`python -c "import torch;print(torch.__version__)"` 输出带 `+cpu`；`pip download` 的总体积明显小于 1 GB。

### P0-4 发布模型时同步导出 OpenVINO，HTTP 挂死

- **位置**：`app/api/train.py:131-135`（同步 `def publish`）→ `train_svc.publish_job` → `app/services/model_svc.py:87-88` → `engine.export_openvino`
- **现状**：OpenVINO 导出在这台 CPU 上要几分钟，全程占着 HTTP 请求，前端必然超时，用户以为发布失败。
- **线索**：`app/tasks.py:156` 的 heavy 任务集合里**已经预留了 `openvino_export` 类型**，但没有注册 handler——上一轮把线铺了一半没接上。
- **改法**：
  1. `publish_job` 拆成两步：**同步**完成模型注册（复制 `.pt`、写 `model` 表）并立即返回 `model_id`；**异步**投递 `openvino_export` 任务
  2. 在 `model_svc` 或 `train_svc` 中 `task_mod.register_handler("openvino_export", ...)`
  3. `model` 表增加 `ov_status` 字段（`pending` / `exporting` / `ready` / `failed`），导出完成后回填 `ov_path`
  4. 预标注加载模型时判断：`ov_status == 'ready'` 才用 OpenVINO，否则退回 `.pt`（保持现有的优雅降级）
  5. 前端模型仓库页展示 OpenVINO 状态，导出中显示"加速版本准备中…"
- **验收**：点发布后接口 **2 秒内**返回；模型立刻可用（走 `.pt`）；几分钟后 `ov_status` 变 `ready`，此后预标注走 OpenVINO。

### P0-5 续训绕过重任务互斥锁

- **位置**：`app/tasks.py:149-157` 的 heavy 集合，对照 `app/services/train_svc.py:566-568` 注册的任务类型名
- **现状**：heavy 集合里是 `"train"`，但续训注册的类型名是 `"train_resume"`，不在集合内 → 续训不进互斥锁，可以和预标注、跟踪等重任务同时抢那 14 个核，双方都慢一倍。
- **改法**：heavy 集合补上 `"train_resume"`。建议顺手把这个集合提成 `app/config.py` 里的常量 `HEAVY_TASK_TYPES`，避免以后新增任务类型再漏。
- **验收**：启动一个续训任务，同时发起预标注，预标注任务状态应显示"等待其他重任务结束…"而不是立刻开跑。

### P0-6 视频导入同步阻塞，无进度反馈

- **位置**：`app/api/datasets.py:91-100`（`import_video` 内直接调同步抽帧）
- **现状**：大视频抽帧（最多 5000 帧）阻塞 HTTP 请求几十秒到几分钟，前端只有一句静态文案"正在抽帧…"（`app.js:179`），没有真实进度。违反设计文档「超 10 秒操作必须有进度反馈」。
- **改法**：
  1. 接口只负责**接收并落盘**视频文件，然后创建 `video_import` 后台任务并立即返回 `task_id`
  2. 注册 `video_import` handler，抽帧过程中按帧数更新 `task.progress`
  3. 该任务类型加入 heavy 集合（抽帧也吃 CPU）
  4. 前端复用已有的 `pollTask` 轮询显示百分比
  5. 抽帧**边抽边写盘**，不要把所有帧攒在内存里（5000 帧会吃掉几个 GB）
- **验收**：传一个 5 分钟视频，接口秒回，前端进度条从 0% 平滑走到 100%。

### P0-7 pid 存活检测不可靠，可能永久卡死训练队列

- **位置**：`app/services/train_svc.py:576-600`（`recover_interrupted_jobs`），判断依据是 `os.kill(pid, 0)`
- **说明**：这条 kimi 的原始描述（"服务停止留孤儿进程"）在你的 Docker 部署下**不成立**——容器停止会杀光容器内所有进程。但底下压着一个真实隐患：
- **真实问题**：容器重启后 pid 从小数字重新分配，**很容易被别的进程复用**。一旦 `os.kill(pid, 0)` 把无关进程误判成"训练还活着"，那条 job 会永远停在 `running` 状态，而 heavy 互斥锁被它占死，**后续所有训练任务永久排队**。
- **改法**：不要只靠 pid。采用下列任一（推荐第 1 种，最简单可靠）：
  1. 训练进程每个 epoch 往 `run_dir/heartbeat` 写一次时间戳；恢复扫描时若心跳超过 10 分钟未更新，判定为已死
  2. 记录 pid 的同时记录进程启动时间（`/proc/<pid>/stat` 第 22 字段），恢复时比对，不一致说明是复用的 pid
- **另外**：无论判定结果如何，**都要保证 heavy 锁不会被幽灵任务永久占用**。建议给锁加超时/看门狗，或在恢复流程里强制释放。
- **验收**：训练跑到一半 `docker compose restart`，重启后任务显示"已中断"并可点「继续训练」；此时新建训练任务不会被卡住。

## 三、P1 —— 应修（影响日常使用和数据质量）

### P1-1 训练数据校验被放水

- **位置**：`app/services/train_svc.py:160-164`
- **现状**：`min_boxes_per_class=1`，而设计文档要求 **10**；错误文案也跟着写成了"每个类别至少要有 1 个框"。
- **风险**：一个类别只有 1~2 个框就允许开训，在 CPU 上白跑几个小时，最后模型完全不可用。
- **改法**：改回 `min_boxes_per_class=10`，错误文案同步改成 10。若确实想放宽，做成 `config.MIN_BOXES_PER_CLASS` 可配置，默认 10；框数在 10~30 之间时不阻断但返回 warning，前端黄色提示"某类样本偏少，训练效果可能不佳"。`export_svc.validate_for_train` 已经生成了 warnings，但目前**没有任何消费方**，一并接到接口返回里。

### P1-2 微调默认 20 轮是死代码

- **位置**：`app/services/train_svc.py:169-171`，根因见第一章
- **现状**：`if is_ft and "epochs" not in params` 永不成立（`schemas.py:83` 的 `epochs: int = 40` 保证了 params 永远有这个键），所以微调实际仍跑 40 轮，白白多花一倍时间。
- **改法**：`schemas.py` 的 `TrainRequest.epochs` 改为 `Optional[int] = None`；`train_svc` 里按 `is_ft` 决定默认值（微调 20，从零 40）。前端表单在切换底模分组时，把轮次输入框的显示值同步改掉，让用户看得见。

### P1-3 C 键复制的是错的那张图

- **位置**：`web/js/labeler.js:584-597`（`copyPrev`），`lastBoxesCopy` 赋值点在 `:537` 和 `:570`
- **现状**：`lastBoxesCopy` 只在**保存时**更新。如果上一张图没有任何改动（不 dirty、不触发保存），它就还停留在更早某张图的标注上，`C` 键复制过来的内容是错的。
- **改法**：改为在**切换图片时无条件**记录"刚离开那张图的 boxes"（无论是否改动过），存进 `lastBoxesCopy`。
- **验收**：图 1 有 2 个框 → 翻到图 2（不做任何修改）→ 翻到图 3 按 `C`，应复制到图 2 的框。

### P1-4 SAM 的 LRU 缓存是纯死代码

- **位置**：`app/services/sam_svc.py:46-56`
- **现状**：`_cache_get` / `_cache_put` 定义完整，但**全文件零调用点**。每次点选都要重新编码整张图。
- **影响**：在这台纯 CPU 机器上，MobileSAM 编码一张图要 1.5~3 秒。同一张图连点 5 次就是白等十几秒——SAM 辅助标注的价值基本被抵消了。
- **改法**：
  1. 在推理入口按 `image_id` 先查 `_cache_get`，miss 才编码，编码后 `_cache_put`
  2. 实现设计文档要求的**预编码**：切换到某张图时，后台线程提前把下一张图编码好（`app/services/sam_svc.py` 里的 prefetch stub 补齐）
- **验收**：同一张图第二次点选响应 < 200 ms（第一次仍是 1.5~3 秒）。

### P1-5 训练耗时预估不随三个关键控件刷新

- **位置**：`web/index.html:90`（数据集 select）、`:101`（底模 select）、`:114`（batch input）
- **订正 kimi 的说法**：不是"estimate 全都不刷新"。轮次、尺寸、freeze、only_confirmed 这四个**已经绑了** `@change="refreshEstimate"`（`:112`、`:113`、`:115`、`:116`）。缺的只有上面这**三个**控件。
- **后果**：换数据集（图片数量差十倍）、换底模（n 和 s 差 3 倍）都不会重算耗时，用户看到的是上一次的预估值，直接误导决策。
- **改法**：给这三个控件补 `@change="refreshEstimate"`。底模 select 注意与已有的 `onGroupChange` 协同，避免重复请求。建议 `refreshEstimate` 加 300 ms 防抖。

### P1-6 去重用的是 aHash 不是 pHash，且 O(n²) 比较

- **位置**：`app/services/dedup_svc.py:16-23`（`_average_hash`）、`:55-73`（两两比较）
- **现状**：实现的是平均哈希（缩放到 8×8 取灰度均值），设计文档要求的是 pHash（需要做 DCT 变换）。aHash 对亮度变化非常敏感——**卡口图片白天黑夜差异大，正是 aHash 最不擅长的场景**，会大量漏判。
- **改法**：
  1. 改成真正的 pHash：缩放到 32×32 → DCT → 取左上 8×8 低频区（排除直流分量）→ 与中位数比较取二值。numpy 实现即可，不必引新依赖
  2. O(n²) 全量两两比较在 5000 张时是 1250 万次，会卡。改用**汉明空间分桶**（把 64 位哈希切成 4 段 16 位，同段相同的才进入精确比较），或用 BK-tree
- **验收**：5000 张图的去重任务在 2 分钟内完成；同一场景白天/夜间的两张图不会被误判为重复。

### P1-7 任务线程池轻重不分

- **位置**：`app/tasks.py:35`（`max_workers=2`）+ `:18` 全局单把 `_heavy_lock`
- **现状**（这条是我复核时新发现的，不在 kimi 清单里）：整个系统只有 2 个 worker 名额，重任务又靠一把全局锁串行。结果是**重任务排队时会把 2 个名额占住**，轻任务（缩略图生成、导出小文件等）跟着一起堵。
- **改法**：拆成两个池——`heavy_executor(max_workers=1)` 负责训练/预标注/跟踪/导出，`light_executor(max_workers=4)` 负责其余。重任务池本身就是 1 个 worker，天然串行，可以顺带干掉那把全局锁（也就同时解决了 P0-7 里"锁被幽灵任务占死"的隐患）。
- **验收**：训练进行中，浏览数据集、生成缩略图等操作依然流畅无卡顿。
