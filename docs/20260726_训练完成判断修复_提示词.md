## 零、背景：一次真实事故

用户提交了 40 轮训练，跑到第 27 轮时因为出差把电脑睡眠了。第二天开机发现：

- 界面显示 **训练成功**，轮次 **40/40**
- 但 `results.csv` 只有 28 行（表头 + 27 行数据）——**实际只跑了 27 轮**
- `train.log` 里没有 `40 epochs completed`、`Optimizer stripped` 等完成标志
- 「继续训练」按钮**不显示**，因为它只在 `interrupted/failed/canceled` 状态下出现

结果：一个没收敛的半成品模型被当作正式版本评估，用户还因此怀疑是数据质量问题，白白排查了半天。

**要不是用户自己记得关过机，这个模型就会被当成品用下去。**

## 一、P0-1 ★ 训练中断被误报为成功

### 根因 A：只看退出码不足以判断训练是否完成

`app/services/train_svc.py:464`：

```python
if proc.returncode != 0:
    update_job(job_id, status="failed", ...)
    raise RuntimeError(...)
# 走到这里就认为成功
```

电脑睡眠/关机时，系统给训练进程发 `SIGTERM`，ultralytics 捕获信号后**正常退出，返回码是 0**。于是代码判定"训练成功"。

**退出码 0 只能说明进程没崩，不能说明训练跑完了。**

### 根因 B：`last_epoch` 被硬编码成目标轮数

`app/services/train_svc.py:483`：

```python
update_job(job_id, status="success", ..., last_epoch=epochs, ...)
                                          # ↑ 写死成 40，覆盖掉轮询解析出的真实值 27
```

轮询循环本来已经从日志正确解析出真实轮次（`:456` 的 `last_epoch=last_epoch`），收尾时被这一行覆盖了。

### 改法

训练进程退出后，**以 `results.csv` 的实际数据行数为准**判断是否跑完：

```python
def _count_epochs(csv_path: Path) -> int:
    """results.csv 每轮一行（不含表头），行数即已完成轮数。"""
    if not csv_path.is_file():
        return 0
    try:
        with open(csv_path, "r", encoding="utf-8", newline="") as f:
            return sum(1 for _ in csv.DictReader(f))
    except Exception:
        return 0
```

替换现在的完成分支：

```python
actual = _count_epochs(run_dir / "results.csv")
last_pt = run_dir / "weights" / "last.pt"

if proc.returncode != 0 or actual < epochs:
    # 注意：状态用 interrupted 而不是 failed —— last.pt 还在，可以续训
    update_job(
        job_id,
        status="interrupted",
        last_epoch=actual,
        finished_at=db.utcnow(),
        pid=None,
        resume_from=str(last_pt) if last_pt.is_file() else None,
        metrics=_read_metrics(run_dir / "results.csv"),   # 部分指标仍然有参考价值
    )
    append_log(
        log_path,
        f"训练未完成：目标 {epochs} 轮，实际完成 {actual} 轮"
        f"（退出码 {proc.returncode}）。可点「继续训练」从断点接着跑。",
    )
    return

# 真正完成
update_job(job_id, status="success", last_epoch=actual, ...)   # ← 用真实值，不要用 epochs
```

**注意区分 `interrupted` 和 `failed`**：

- 进程崩溃/参数错误 → `failed`（`last.pt` 可能不存在或不可用）
- 被系统信号终止、轮次没跑够但 `last.pt` 完好 → `interrupted`（可续训）

判据：`last.pt` 存在且 `actual > 0` 就算 `interrupted`，否则 `failed`。

### 前端

训练任务卡片上把轮次显示成 **`27 / 40`**（已完成 / 目标），现在只显示一个数字，看不出来跑没跑完。`interrupted` 状态要有醒目的黄色标记和「继续训练」按钮（按钮逻辑已存在于 `web/index.html:246`，只要状态对了就会出现）。

### 验收

1. 提交一个 20 轮的训练，跑到第 5 轮左右时手工 `kill <训练进程pid>`（**用 SIGTERM，模拟系统关机**：`kill <pid>`，不要用 `kill -9`）
2. 任务状态必须是 **`interrupted`**，`last_epoch` 等于 `results.csv` 的真实行数，**不是 20**
3. 界面出现「继续训练」按钮，点击后能从断点继续，最终跑满 20 轮
4. 跑满后状态才是 `success`，且 `last_epoch` 等于真实完成轮数

## 二、P0-2 ★ 记录的指标不是 best.pt 的指标

### 现状

- `best_pt` 字段指向 `weights/best.pt`（ultralytics 按 fitness 选出的**历史最优**权重）
- 但 `metrics` 来自 `_read_metrics()`（`train_svc.py:492`），取的是 `results.csv` 的**最后一行**，即**最后一轮**的指标
- **训练结束后没有跑验证**（全项目搜不到 `detect val` 调用）

早停触发时，最后一轮往往不是最优轮（patience=10 意味着最后 10 轮都没改善）。实际案例：某次训练 best 在第 32 轮，指标却记的是第 40 轮的。

**后果**：用户看到的指标，和他实际发布、实际使用的那个模型，不是同一个东西。这会让每一版的横向对比都偏一点，而且偏差不固定，很难察觉。

### 改法

训练正常完成后，**用 `best.pt` 跑一次验证**，把真实指标写进 `metrics`：

```python
# 训练成功后追加
val_cmd = [
    _resolve_yolo_bin(), "detect", "val",
    f"model={best_pt}", f"data={yaml_path}",
    f"imgsz={imgsz}", "device=cpu", "verbose=True",
    f"project={run_dir}", "name=val_best", "exist_ok=True",
]
```

- 从 val 的输出或其 `results.csv` 解析 mAP50 / mAP50-95 / precision / recall
- 存进 `metrics` 时**标明来源**，例如加一个字段 `"metrics_from": "best.pt val"`
- val 失败不要让整个任务失败：降级回 `_read_metrics()` 读最后一轮，并在 `metrics` 里标 `"metrics_from": "last epoch (val failed)"`
- val 也吃 CPU，但只跑一遍验证集，几十秒量级，可以接受

另外 `_read_metrics()` 保留，但改成**找 fitness 最高的行**而不是最后一行（用作 val 失败时的兜底）。ultralytics 的 fitness 默认是 `0.1*mAP50 + 0.9*mAP50-95`，可以直接按这个公式在 `results.csv` 里算。

### 验收

1. 训练一版会触发早停的模型（epochs 设大一点，比如 60 + patience 10）
2. 训练完成后，`metrics` 中的 `mAP50-95` 必须等于**用 `best.pt` 单独跑 val 的结果**（手工执行 `yolo detect val model=best.pt data=... imgsz=416 device=cpu` 核对）
3. `metrics` 里能看出指标来源
4. 人为把 `best.pt` 删掉，val 失败 → 任务仍然成功，`metrics_from` 标明是兜底值

## 三、P1 切图质量过滤

### 背景

用真实数据跑「智能切图导入」后，切出的图里混有明显无效的样本：

- **纯黑/极暗**的切图（夜间画面的暗部区域）
- **只有身体没有头**的切图（person 框位置偏，或人被前车遮挡）

这些图标也没法标，还会占用标注人力、拖累训练。实测 40 张切图里约有 5~8 张属于这类。

### 改法

`app/services/crop_svc.py` 的切图循环里，生成 crop 之后、入库之前加两条过滤（阈值都要可配，放进 `_DEFAULT_PARAMS`）：

```python
"min_brightness": 25,      # 平均亮度低于此值丢弃（0~255）
"min_aspect": 0.5,         # 宽高比下限
"max_aspect": 3.0,         # 宽高比上限
```

- **亮度**：转灰度取 `np.asarray(crop.convert("L")).mean()`，低于 `min_brightness` 丢弃
- **宽高比**：`w/h` 超出 `[min_aspect, max_aspect]` 丢弃（异常比例往往是框错了）
- 被过滤的数量要**分类统计**并写进任务完成消息：
  ```
  处理大图 405 张，检出目标 2456 个，跳过过小 892 个，
  跳过过暗 63 个，跳过比例异常 41 个，切图入库 1460 张
  ```
- 预览接口也要应用同样的过滤，保证预览所见即入库所得

**阈值要保守**：宁可放进来几张暗图让人工跳过，也不要误删有效样本。`min_brightness=25` 是很暗的水平（正常夜间切图实测亮度在 60~80），先用这个值，不够再调。

### 验收

1. 用同一批原图跑切图，完成消息里能看到"跳过过暗 N 个、跳过比例异常 M 个"
2. 抽查被过滤掉的切图（可以临时打日志记文件名），确认确实是无效样本，**没有误伤正常骑手**
3. 预览结果与全量入库结果的过滤行为一致
